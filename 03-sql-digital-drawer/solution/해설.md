이 문서는 **평가 때 내 말로 설명하기** 위한 공부 노트입니다. 위에서부터 차례로 읽으세요.

## 1. 데이터베이스는 엑셀과 뭐가 달라요?

엑셀에 리뷰를 적는다고 해볼게요.

| 회원 | 회원 이메일 | 작품 | 화가 | 화가 국적 | 별점 |
|---|---|---|---|---|---|
| 민지 | minji@… | Irises | 고흐 | Dutch | 5 |
| 민지 | minji@… | Sunflowers | 고흐 | Dutch | 4 |
| 서준 | seojun@… | Irises | 고흐 | Dutch | 3 |

문제점:
- "고흐 / Dutch"가 **계속 반복**돼요. 고흐 정보를 고치려면 줄마다 다 고쳐야 해요. 하나라도 빼먹으면 서로 말이 안 맞게 돼요.
- 민지가 이메일을 바꾸면 민지가 쓴 줄을 모두 찾아서 고쳐야 해요.

데이터베이스는 이걸 **주제별 표로 나눠서** 저장해요.
- 화가 정보는 `artist` 표에 **딱 한 번**만
- 회원 정보는 `member` 표에 **딱 한 번**만
- 리뷰 표에는 "몇 번 회원이 몇 번 작품에 몇 점"만 번호로 적기

> 💬 **한 줄 답**: "엑셀은 한 장에 다 적어서 같은 정보가 반복되지만, DB는 주제별 표로 나누고 **관계(번호)**로 연결해서 한 곳만 고치면 되게 만듭니다."

## 2. PK와 FK가 뭐예요?

- **PK (Primary Key, 기본키)** = 각 줄의 **주민등록번호**예요. 표 안에서 절대 겹치지 않아요.
  - `artist.id = 11` → 고흐
- **FK (Foreign Key, 외래키)** = **다른 표의 PK를 적어두는 칸**이에요.
  - `artwork.artist_id = 11` → "이 작품은 11번 화가(고흐)가 그렸다"

### 1:N 관계
"하나가 여러 개를 가진다"는 뜻이에요.

```
artist (화가)  1 ──── N  artwork (작품)    고흐 1명 → 작품 4점
member (회원)  1 ──── N  review  (리뷰)    민지 1명 → 리뷰 여러 개
artwork(작품)  1 ──── N  review  (리뷰)    Irises 1점 → 리뷰 여러 개
```

규칙: **FK는 항상 N 쪽(많은 쪽) 표에 들어가요.** 작품마다 화가가 한 명이니까 작품 표에 `artist_id`를 적어요. 화가 표에 작품 번호를 적으려면 칸이 끝없이 필요해서 안 돼요.

### FK가 "막는다"는 게 뭐예요?
`bonus.sql`의 B03, B04에서 실제로 해봤어요.
- **없는 999번 화가의 작품을 넣으려고 하면** → `FOREIGN KEY constraint failed` 에러가 나요. 존재하지 않는 화가를 가리키면 안 되니까요.
- **리뷰가 달린 작품을 지우려고 하면** → 이것도 에러가 나요. 지우면 "주인 없는 리뷰"가 생기니까요.

⚠️ **SQLite만의 특징**: FK 검사가 기본으로 **꺼져 있어요**. 그래서 파일마다 `PRAGMA foreign_keys = ON;`을 적었어요.

### 다른 제약조건
| 제약 | 뜻 | 이 DB에서 |
|---|---|---|
| NOT NULL | 비워두면 안 됨 | 작품 제목, 회원 이메일 |
| UNIQUE | 겹치면 안 됨 | 화가 이름, 회원 이메일, (회원+작품) 리뷰 조합 |
| CHECK | 조건에 맞아야 함 | 별점 1~5, 미술관은 met/aic/cma 중 하나 |

## 3. SELECT / INSERT / UPDATE / DELETE 언제 써요?

| 명령 | 뜻 | 비유 | 예 |
|---|---|---|---|
| `SELECT` | 꺼내 보기 | 서랍 열어서 보기 | Q01~Q12 |
| `INSERT` | 새로 넣기 | 서랍에 새 종이 넣기 | data.sql 전체 |
| `UPDATE` | 고치기 | 종이 내용 고쳐 쓰기 | Q13 (별점 2→4) |
| `DELETE` | 지우기 | 종이 버리기 | Q14 (14번 리뷰) |

⚠️ UPDATE와 DELETE에는 **`WHERE`를 꼭 붙여요.** `WHERE` 없이 `DELETE FROM review;`를 실행하면 리뷰가 **전부** 지워져요.

## 4. SELECT 문은 이렇게 읽어요

```sql
SELECT title, year_made      -- ③ 어떤 칸을 보여줄까
FROM artwork                 -- ① 어느 표에서
WHERE year_made >= 1880      -- ② 어떤 줄만 고를까
ORDER BY year_made DESC      -- ④ 어떤 순서로 (DESC = 큰 것부터)
LIMIT 5;                     -- ⑤ 몇 개만
```
실제 실행 순서는 ① FROM → ② WHERE → ③ SELECT → ④ ORDER BY → ⑤ LIMIT 이에요.

## 5. JOIN — 나눈 표를 다시 붙이기

리뷰 표에는 번호만 있어요. `member_id = 9`, `artwork_id = 43`처럼요. 사람이 읽으려면 이름이 필요하니까 **표를 옆으로 붙여요.**

```sql
FROM review r
INNER JOIN member m ON r.member_id = m.id    -- 리뷰의 회원번호 = 회원표의 번호인 것끼리 붙인다
```

### INNER JOIN vs LEFT JOIN
- **INNER JOIN**: 양쪽 모두 짝이 있는 줄만 남겨요. → Q05, Q06, Q07
- **LEFT JOIN**: 왼쪽 표는 **전부** 남기고, 짝이 없으면 오른쪽을 `NULL`(빈칸)로 채워요. → Q08

Q08이 핵심이에요. 작품(왼쪽)에 리뷰(오른쪽)를 LEFT JOIN 하면, 리뷰가 없는 작품은 `review_id`가 NULL이 돼요. 그래서 `WHERE r.id IS NULL`로 **리뷰가 하나도 없는 작품**을 찾을 수 있어요.

> 💬 **한 줄 답**: "INNER는 짝이 있는 것만, LEFT는 왼쪽은 다 보여주고 짝이 없으면 NULL입니다. 그래서 '없는 것 찾기'는 LEFT JOIN + IS NULL로 합니다."

## 6. GROUP BY + 집계 — 묶어서 세기

`GROUP BY`는 **같은 값끼리 바구니에 담는 것**이고, 집계 함수는 **바구니마다 계산하는 것**이에요.

| 함수 | 뜻 | 쿼리 |
|---|---|---|
| `COUNT` | 몇 개? | Q09 국적별 작품 수 |
| `AVG` | 평균은? | Q10 화가별 평균 별점 |
| `SUM` | 합계는? | Q11 회원별 별점 합계 |

**WHERE vs HAVING**
- `WHERE` = 바구니에 담기 **전에** 한 줄씩 거르기
- `HAVING` = 바구니에 담은 **후에** 바구니 단위로 거르기 (Q10: 리뷰 3개 이상인 화가만)

## 7. 서브쿼리 — 쿼리 안의 쿼리

```sql
SELECT nickname FROM member
WHERE id NOT IN (SELECT member_id FROM review);   -- 괄호 안부터 실행
```
1. 괄호 안: "리뷰를 쓴 회원 번호 목록"을 구해요 → 1, 2, 3 … 11
2. 바깥: 그 목록에 **없는** 회원을 골라요 → 12번 나리

**JOIN vs 서브쿼리 비교 (보너스 B01, B02)**: 결과로 나오는 리뷰는 같아요. 하지만 JOIN은 다른 표의 칸(작품 제목)도 같이 보여줄 수 있고, 서브쿼리는 거르는 용도라서 읽기 쉬워요.

## 8. 인덱스 — 책 뒤의 "찾아보기"

인덱스가 없으면 DB는 `artwork_id = 9`인 리뷰를 찾으려고 리뷰를 **처음부터 끝까지 다 봐요** (`SCAN`).
인덱스를 만들면 책 뒤 색인처럼 **바로 그 위치로 가요** (`SEARCH … USING INDEX`).

Q15 결과를 보면 실제로 바뀌어요.
```
만들기 전: SCAN review
만든 후:   SEARCH review USING INDEX idx_review_artwork_id (artwork_id=?)
```

**어떤 칸에 만들어요?** WHERE나 JOIN에 **자주 쓰이는 칸**에 만들어요. FK 칸이 대표적이에요.
**단점은?** 데이터를 넣거나 고칠 때 인덱스도 같이 고쳐야 해서 쓰기가 조금 느려지고, 저장 공간도 더 써요. 그래서 아무 칸에나 만들지 않아요.

PK 칸에는 SQLite가 인덱스를 자동으로 만들어요. UNIQUE 칸도 마찬가지예요.

## 9. 예상 질문 — 소리 내서 답해보기

답을 가리고 먼저 말해본 다음 확인하세요.

<details><summary>Q. 왜 표를 4개로 나눴어요?</summary>
화가·작품·회원·리뷰는 각각 독립된 대상이에요. 한 표에 넣으면 화가 정보가 리뷰마다 반복되고, 고칠 때 여러 곳을 고쳐야 해요. 나누면 한 곳만 고치면 돼요.
</details>

<details><summary>Q. 1:N 관계를 이 DB에서 하나 설명해 보세요.</summary>
화가 1명은 작품 여러 점을 그려요. 그래서 N 쪽인 artwork 표에 artist_id라는 FK를 두고 artist.id를 가리키게 했어요.
</details>

<details><summary>Q. review 표에는 FK가 왜 2개예요?</summary>
리뷰는 "누가(회원)"와 "무엇을(작품)" 둘 다에 속해요. 회원 1:N 리뷰, 작품 1:N 리뷰 관계가 둘이라서 FK도 둘이에요.
</details>

<details><summary>Q. FK가 동작한다는 걸 어떻게 보여줘요?</summary>
bonus.sql B03에서 없는 999번 화가로 작품을 넣으면 "FOREIGN KEY constraint failed" 에러가 나요. SQLite는 PRAGMA foreign_keys = ON 으로 켜야 해요.
</details>

<details><summary>Q. UNIQUE (member_id, artwork_id) 는 왜 넣었어요?</summary>
한 회원이 같은 작품에 리뷰를 여러 번 쓰면 평균 별점이 왜곡돼요. 두 칸 조합이 겹치지 않게 막았어요.
</details>

<details><summary>Q. INNER JOIN과 LEFT JOIN 차이는요?</summary>
INNER는 양쪽 다 짝이 있는 줄만, LEFT는 왼쪽 표는 모두 남기고 짝이 없으면 NULL로 채워요. Q08에서 리뷰 없는 작품 21점을 LEFT JOIN + IS NULL로 찾았어요.
</details>

<details><summary>Q. WHERE와 HAVING 차이는요?</summary>
WHERE는 묶기 전 한 줄씩, HAVING은 GROUP BY로 묶은 뒤 그룹 단위로 걸러요. Q10에서 "리뷰 3개 이상인 화가"는 묶어서 세야 알 수 있으니 HAVING을 썼어요.
</details>

<details><summary>Q. 인덱스를 왜 review.artwork_id 에 만들었어요?</summary>
"이 작품의 리뷰 보기"와 작품-리뷰 조인이 가장 자주 일어나는 칸이라서요. EXPLAIN QUERY PLAN 결과가 SCAN에서 SEARCH USING INDEX로 바뀌었어요.
</details>

<details><summary>Q. 인덱스를 모든 칸에 만들면 안 돼요?</summary>
INSERT/UPDATE/DELETE 때마다 인덱스도 고쳐야 해서 느려지고 공간도 더 써요. 자주 검색하는 칸에만 만들어요.
</details>

<details><summary>Q. 데이터는 어디서 왔어요?</summary>
화가와 작품은 제 다른 프로젝트(AITOOLLEARN-7-1)의 명화 DB에서 가져왔어요. 메트로폴리탄(MET), 시카고 미술관(AIC), 클리블랜드 미술관(CMA)이 CC0(저작권 없이 자유 이용)로 공개한 데이터예요. 회원과 리뷰는 연습용으로 지어낸 데이터예요.
</details>
