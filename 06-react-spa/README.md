# 6. 버튼 누르면 화면이 스르륵 바뀌는 요즘 웹사이트 만들기 — React SPA — 마감 10/27

## 1. 미션 소개
어떤 상태가 어디에 있어야 하는지, 언제 리렌더링이 일어나는지 이론만으로는 감이 잘 안 잡힙니다. 상태 관리가 왜 어려운지는 SPA를 직접 만들어봐야 알 수 있습니다. 컴포넌트 구조와 데이터 흐름을 결과물로 확인하는 것, 그게 이번 미션의 목표입니다.

이 미션에서는 React로 하나의 SPA 서비스를 직접 구현하며, 컴포넌트 설계, 라우팅, 상태 관리, 비동기 데이터 처리의 흐름을 체계적으로 경험합니다. "사용자 이벤트 → 상태 변화 → 렌더링 변화"가 연결되는 React의 동작 원리를 결과물로 확인합니다.

또한 Supabase 또는 Firebase를 최소 범위로 연동하여, 로딩/에러/빈 상태를 일관된 UI 패턴으로 처리하는 경험을 쌓습니다. 평가는 백엔드 구현이 아니라 React 관점의 구조와 데이터 흐름 완성도 중심입니다.

## 2. 최종 결과물
React 기반 웹 서비스 1개 (백엔드는 Supabase 또는 Firebase 중 택1)
- **라우팅이 있는 SPA**: 최소 5개 이상 페이지 라우트 (예: /, /login, /items, /items/:id, /items/new, /profile)
- **핵심 데이터 CRUD**: 게시물/할 일/리뷰/예약 등 핵심 데이터 등록/조회/수정/삭제, 목록 페이지와 상세 페이지 존재
- **React 폼 기반 입력 경험**: 등록/수정 화면에 폼, 유효성 검증 + 에러 표시 + 제출 중 상태
- **상태 관리가 설계된 UI**: 로딩/에러/빈 상태가 모든 핵심 화면에서 일관되게 처리, 컴포넌트 단위로 상태 분리
- **배포**: 외부 접속 가능한 URL(Vercel/Netlify 등), GitHub 레포지토리 URL, README.md에 실행 방법과 기술 스택 명시

## 3. 과제 목표
- 컴포넌트가 왜 필요한지, 어떤 기준으로 쪼갰는지 설명할 수 있다.
- props와 state의 차이, 상태를 어디에 두었는지(상향/하향 흐름) 설명할 수 있다.
- useEffect가 언제 실행되고, 어떤 의존성으로 동작하며, 데이터 요청과 어떤 관계가 있는지 설명할 수 있다.
- 비동기 흐름에서 로딩/성공/실패/빈 상태를 React UI로 어떻게 표현했는지 설명할 수 있다.
- 라우팅 → 컴포넌트 → 상태 → 이벤트 → 렌더링이 어떻게 연결되는지 설명할 수 있다.

## 4. 기능 요구 사항
### 프로젝트 기본 구성
- React 프로젝트, 폴더 구조: pages(라우트 단위 화면), components(재사용 컴포넌트), hooks 또는 lib(커스텀 훅/유틸)
- 공통 레이아웃(헤더/네비게이션)이 주요 페이지에 적용
- 서비스 주제는 직접 정하되, 단일 핵심 데이터 CRUD 수준

### 라우팅(React Router 등)
- 최소 5개 라우트, 목록/상세 라우트 포함(/items, /items/:id)
- 잘못된 주소 접근 시 Not Found 페이지
- 네비게이션으로 주요 라우트 이동 링크 제공

### 컴포넌트 설계
- 최소 8개 이상 재사용 컴포넌트 (Button, Input, Card, EmptyState, ErrorState, Loading, ItemList, ItemForm 등), 최소 1개 이상 prop을 받아 동작/표시가 달라짐
- 페이지 컴포넌트와 UI 컴포넌트 분리
- 로딩/에러/빈 상태 UI는 재사용 컴포넌트로 통일

### 상태 관리(React 중심)
- 폼 입력 상태(controlled input), 목록/상세 데이터 상태, 로딩/에러 상태
- 데이터 조회/갱신 흐름 중 최소 1개는 커스텀 훅으로 분리 (useItems(), useItemDetail(id) 등)

### CRUD (Supabase 또는 Firebase 원격 데이터 기준)
- 목록 조회: 리스트 UI 렌더링
- 상세 조회: 라우트 파라미터로 특정 데이터 불러와 렌더링
- 등록/수정: 폼 입력 → 제출 → 성공 시 이동/갱신
- 삭제: 삭제 후 목록 갱신 또는 이동

### 폼 UX
- 필수값 검증(제목/내용 비어있으면 제출 불가)
- 에러 메시지가 입력 필드 근처 또는 상단에 표시
- 제출 중 버튼 비활성화 또는 스피너
- 요청 실패 시 실패 사실이 화면에 표시

### React 이벤트 & 렌더링
- 사용자 이벤트가 상태 변경 → 렌더링 변화로 이어지는 지점 최소 3군데 (필터 변경 → 목록 변경, 입력값 변경 → 미리보기 변경, 저장 성공 → 알림 표시 등)

### 배포
- 배포된 URL에서 목록/상세 조회, 등록/수정/삭제 모두 동작
- 환경변수 누락으로 일부라도 동작하지 않으면 미충족

## 5. 보너스 과제 (선택)
- 전역 상태 도입: 로그인 사용자, 테마, 알림 중 하나를 Context 등으로 관리
- 성능 최적화: useMemo/useCallback/React.memo 중 1개 이상 적용
- 인증 추가: Supabase/Firebase Auth 로그인 흐름 + 보호 라우트

## 6. 개발 환경
React 18 이상

## 7. 제약 사항
- React 기반, 핵심 목표는 컴포넌트/상태/이벤트/비동기 렌더링 학습
- 백엔드: Supabase 또는 Firebase, 고급 기능(권한/RLS/Rules 등)은 필수 아님
- 라우팅 존재, 페이지/컴포넌트/훅(또는 lib) 분리
- UI 고퀄리티보다 React 구조와 데이터 흐름 우선, 백엔드 서버 직접 구현 불필요
- TypeScript 선택 사항(가산점 없음), 스타일링 자유(순수 CSS/CSS Modules/Tailwind/styled-components/MUI 등), 반응형 선택
- API Key 등 민감 정보는 .env에 저장하고 .gitignore 확인, GitHub에 절대 푸시 금지, 배포 시 대시보드에 Environment Variables 등록

## 8. 결과 예시
- /items에서 카드 리스트가 보이고, 로딩 중에는 스피너
- 리스트 항목 클릭 시 /items/123로 이동하고 상세가 뜸
- /items/new에서 폼 작성 후 저장하면 목록 또는 상세로 이동
- 빈 데이터면 "표시할 데이터가 없습니다."
- 에러면 "요청에 실패했습니다. 다시 시도하세요."
